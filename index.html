컴포넌트 JSON 스키마 추상화

Problem
ComfyUI 기반이라 모델·기능마다 필요한 파라미터 조합이 전부 달랐고(사이즈·스텝·프리셋·style strength ...), 기능이 추가될 때마다 프론트에 새 UI를 매번 붙이는 방식이 반복돼 확장 속도가 붙지 않았습니다.
Solution
프롬프트 외 파라미터를 JSON 스키마로 추상화하고, 프론트에는 공통 컴포넌트(Select · Slider · File · AspectRatio · Presets)만 유지. 백엔드는 기능당 스키마 파일 하나로 UI를 선언하고, 프론트가 스키마를 해석해 자동 렌더링합니다.
Impact
신규 모델·기능 추가가 스키마 정의로 축소. 1·2·3차 계약 동안 SD3.5 → Flux → Kontext → Nunchaku 로의 모델 전환·확장을 UI 리팩터 없이 반복적으로 수행.
Limit
스키마가 파일이라 신규 모델 추가 시 재배포가 필요했고, 비개발자는 편집할 수 없었습니다 → 다음 프로젝트(PlusX GenAI)에서 DB로 이전.
  • 편집 기능 API 개발 — Remove · Inpaint · Outpaint · Image Combine · Hand Fixer · Advanced Upscale · Product · CMF · Prompt Edit 등의 백엔드 API 담당.
  • 모델 확장 (API 관점) — SD3.5 → Flux Dev/Krea/Fill 전환, Kontext LLM 기반 자연어 편집(T2T), Nunchaku 경량화 모델 도입에 맞춰 API·스키마 확장.
  • 온프레미스 하드웨어 제약 대응 (자발 제안) — 온프레미스 환경이라 스토리지가 제한적인 상황. 클라이언트 요청이 없었지만 일 단위로 DB·이미지 데이터를 조회해 잔여 이미지를 정리하는 스케줄러를 직접 만들어 반영. I2I 도중 이미지만 첨부하고 이탈하는 케이스, 이미지 삭제 실패로 남는 파일까지 커버.
  • 다국어 대응 (3차) — 해외 디자이너 사용에 맞춰 에러 메시지 다국어 응답과 번역 API 연동 등 백엔드 영역 담당 (UI 텍스트·툴팁은 FE 주도).

JSON 스키마를 DB로 이전

Problem
앞선 삼성 프로젝트에서 잡은 JSON 스키마 추상화 방향은 옳았지만, 스키마가 파일에 있어 모델·파라미터 하나 바꾸려면 배포가 필요했고, 비개발자가 손댈 수 없었습니다. 모델 교체나 장애 대응도 모두 개발자가 직접 진행해야 했습니다.
Solution
스키마 자체를 DB로 이전. 모델 하나당 한 row에 요청 스키마와 UI 스키마를 함께 저장해 워크플로우와 UI가 절대 어긋나지 않게 만들었습니다. UI 컴포넌트는 별도 모델로 카탈로그화해 재사용, 모델별 활성/비활성은 데이터 스위치로 제어.
Impact
신규 모델·기능이 어드민에서 row 추가만으로 즉시 반영. 실제 운영에서 Sagemaker → Flux.1 dev → Fal AI로의 모델 교체를 배포 없이 진행했고, 장애 시 데이터 스위치로 즉시 차단하며 사용자에게 사유 메시지를 노출. 모델별 원가까지 데이터로 관리돼 대시보드 집계에 그대로 사용.

이미지 검색 · 프롬프트 밖의 검색성

Problem
이미지 검색 기능을 얹으려 했을 때, 프롬프트 텍스트 기반 검색만으로는 한계가 있었습니다. 디자인 회사 특성상 유저가 이미지의 '느낌'이나 분위기로 검색하려는 경우가 많은데, 이런 감각은 프롬프트 문구에는 잘 드러나지 않아 별도의 키워드 기반 검색이 필요했습니다.
Solution
이미지 생성이 끝나는 시점에 사내 GPU 서버로 image-to-keyword를 돌려 이미지 자체에서 키워드를 추출하고, 이 키워드를 검색 대상으로 삼도록 했습니다. 그리고 검색 결과가 상위 소수의 이미지에만 쏠리는 문제를 해결하기 위해 가중치 랭킹(키워드 매칭 70% / 조회수 20% / 북마크 10%)을 얹어, 정확도와 다양성을 동시에 확보했습니다.
Impact
프롬프트만으로는 안 걸리던 이미지가 내용 기반으로 검색되기 시작. 인기 이미지에 쏠리던 결과 편중이 완화돼 같은 검색어에도 결과가 매번 다양하게 나오도록 튜닝. 이후 EventLog·SearchLog를 남겨 랭킹 파라미터를 지속 조정할 근거를 확보.

  • Vary · Rerun · Upscale · Comment — 이미지 상세에서 variation 재생성, 파라미터 그대로 재실행, Advanced Upscale, 이미지별 댓글 스레드.

사내 통합 인증 (SSO) 도입

Problem
사내에 컨택트·GenAI 등 서비스마다 자체 계정 DB가 있었습니다. 초기 가입 시점에만 그룹웨어와 연동되고 이후에는 각 서버가 아이디·비밀번호를 따로 저장·관리하는 구조라, 퇴사자 접근을 일일이 서비스마다 끊어야 했고 그룹웨어 비밀번호를 바꿔도 다른 사이트의 비밀번호는 그대로 남았습니다. 계정 관리가 서비스 수만큼 늘어나는 게 문제였습니다.
Solution
회사가 지시한 과제는 아니었습니다. 가능성을 직접 보고 프로토타입으로 검증한 뒤 도입까지 이어간 케이스입니다. 그룹웨어를 사내 통합 인증 서버로 세워(SAML · OAuth 2.0 기반, django-oauth-toolkit 활용) 각 서비스가 여기에 인증을 위임하도록 만들고, 클라이언트 관리·그룹사 SSO 신청 페이지를 어드민에 붙여 신규 서비스 등록도 코드 없이 데이터로 처리되도록 구성했습니다.
Impact
계정이 그룹웨어 단일 소스로 정리돼, 퇴사자 계정 하나만 비활성화하면 모든 서비스 접근이 끊기고 비밀번호도 한 번의 변경으로 전 서비스에 적용됩니다. 최근 사내 바이브 코딩으로 늘어난 신규 서비스들도 별도 계정 설계 없이 그룹웨어 계정에 곧바로 붙일 수 있게 됐습니다.
Bonus
이 과정에서 컨택트 사이트에도 직접 SSO를 얹었는데, React 기반이라 원래는 다루지 않던 스택이었습니다. 프로젝트 구조를 파악하며 직접 연동까지 마무리했습니다.

전자결재 라인 유연화

Problem
기존 결재라인은 팀 단위로 고정돼 있어 결재자를 자유롭게 바꿀 수 없었습니다. 조직 개편, 프로젝트별 결재자 지정, 특정 안건만 다른 승인자를 태우는 케이스 등 운영 요구를 코드 변경 없이 반영할 수 없다는 게 병목이었습니다.
Solution
결재라인을 트리 구조로 재설계했습니다. 기본 뼈대는 팀 계층을 그대로 재사용하되, 그 트리의 어떤 노드에든 임의의 결재자를 삽입·치환할 수 있게 만들었습니다. 안건 단위로 라인을 복제해 편집하는 방식이라 팀 구조는 건드리지 않고 케이스별로 자유롭게 대응합니다.
Impact
순차/비순차, 다단계 결재, 조직 계층 참조를 하나의 모델로 표현. 이후 상위 결재자 자동 위임, 다중 채널 알림, 일괄 승인, 신규 템플릿(워케이션·퇴사·전세자금대출·생일 공가 등)을 구조 수정 없이 데이터로만 확장할 수 있게 됐습니다.

전자결재 Slack 연동 — 결재 속도 개선

Problem
기존 전자결재는 홈페이지에 직접 접속해야 승인·반려·취소가 가능했습니다. 결재자가 다른 업무 중이거나 자리에 없을 때 결재가 지연됐고, 이걸 근본적으로 풀려면 자체 모바일 앱이 필요했지만 앱을 유지·개발할 리소스가 없었습니다.
Solution
전사에 도입된 Slack을 결재 채널로 활용. 결재가 오면 슬랙 메시지에 승인·반려·취소 버튼을 붙여 슬랙 안에서 결재를 완결할 수 있게 했고, 처리 결과는 웹에도 즉시 반영되도록 양방향으로 연결했습니다. 슬래시 커맨드·첨부파일 노출·스레드 업데이트까지 얹어 슬랙만으로도 결재 흐름이 끊기지 않게 만들었습니다.
Impact
결재 회전 속도가 눈에 띄게 빨라졌고, 앱을 만들지 않고도 이미 전사에 깔린 플랫폼(슬랙 알림 · 액션)을 활용해 리소스 대비 최선의 결과를 낸 케이스로 남았습니다.
